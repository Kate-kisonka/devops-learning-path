# Практика · от адреса сайта до записи в PostgreSQL

## Маршрут запроса

1. Браузер определяет адрес по имени хоста и устанавливает HTTPS-соединение с reverse proxy. Прокси выбирает приложение по имени хоста.
2. Веб-сервер отдаёт HTML, CSS и JavaScript. Код страницы запрашивает данные у API и рисует таблицу из ответа JSON.
3. При нажатии «Сохранить» обработчик формы отправляет PATCH. Идентификатор объекта передаётся в URL, изменённые поля — в JSON.
4. API проверяет сессию, права и содержимое запроса. Сервер берёт соединение из пула PostgreSQL, выполняет параметризованный UPDATE и возвращает сохранённые данные.
5. Интерфейс обновляется по ответу сервера. При ошибке интерфейс показывает её, а незавершённая SQL-транзакция откатывается.

## Docker, база и вход

- Если приложение и PostgreSQL находятся в одной сети Compose, приложение может обратиться к PostgreSQL по имени сервиса и внутреннему порту. Адрес 127.0.0.1 ведёт в текущий контейнер.
- Входящий HTTP-трафик и соединение приложения с БД могут идти по разным сетям. Публикация порта прокси не требует публикации порта PostgreSQL.
- PGHOST, PGPORT и PGDATABASE определяют точку подключения и выбранную базу. PGUSER и PGPASSWORD служат для входа приложения в БД. Конфигурация может поступать из окружения или из файлов секретов.
- Сессия веб-панели и соединение с PostgreSQL имеют разные жизненные циклы. Браузер предъявляет cookie приложению. Драйвер БД предъявляет учётные данные серверу PostgreSQL.
- pgAdmin и бэкенд могут подключаться к одной базе независимо друг от друга.

## Самопроверка в учебном контуре

1. Объяснить маршрут запроса вслух от браузера до PostgreSQL и обратно.
2. В DevTools найти запрос сохранения и назвать его метод, URL, поля JSON и код ответа.
3. Сравнить тестовую строку SELECT до и после изменения. Если изменяемое поле находится в связанной таблице, объяснить, по какому внешнему ключу найдена запись.
4. Объяснить, почему сборка образа, публикация в registry и обновление запущенного сервиса — три разных события.
